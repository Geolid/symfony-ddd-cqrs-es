## Source

### Rules

**ALWAYS**
- Rehydrating a date from the database: `new \DateTimeImmutable($value, new \DateTimeZone('UTC'))` — an explicit timezone, otherwise the behavior silently depends on the server's local timezone.
- Binding a `\DateTimeImmutable` into a query (a `WHERE` filter, an `insert()`/`update()` value) passes the object itself with `Doctrine\DBAL\Types\Types::DATETIME_IMMUTABLE` as the parameter type (`setParameter('cutoff', $cutoff, Types::DATETIME_IMMUTABLE)`) — never a hand-formatted string, which duplicates the format Doctrine's own type already owns.
- An Event Store repository's `load()` catches `AggregateNotFound` and re-throws the BC's own `<Aggregate>NotFoundException` — otherwise a vendor exception leaks out as a raw 500 instead of a mapped domain failure.
- A Projector extends `AbstractDbalProjector` — outside that base class it isn't in the `projector` group and its schema is never created.
- A Finder reads `from(<Projector>::TABLE)`, never a re-declared table-name literal — otherwise it silently drifts if the projector's table changes.
- Native `\assert()` narrows a value already guaranteed correct by the calling code, never external/user input. `Webmozart\Assert` stays reserved for a real invariant that must hold in production and throw a catchable exception.

**NEVER**
- Use a raw `HttpClientInterface` outside `Shared\Infrastructure\Gateway`.

### Conventions
- `Infrastructure/` splits into three families. First, is the class a PHP Attribute (`#[\Attribute]`) whose entire role is specializing/aliasing a vendor's own attribute for readability — its constructor only stores configuration a framework reads later by reflection, never executed as part of an actual request/business flow? That's a **proxy** — it stays completely vendor-silent regardless of what it extends underneath (extending a vendor attribute class to rename it is not behavioral coupling, since the class is never instantiated as part of real program flow, only reflected on). It lives bare, named after the role it declares, in that role's own folder — promoted to that folder's parent instead when it would otherwise sit there alone (a lone same-named file in a lone folder adds no information the file itself doesn't already carry), unless the parent's own files are all a different, specific role already — a promotion that would mix in a role its new neighbors don't share keeps its own folder instead, even solo.
- Otherwise, does the class implement one of our own Application/Domain interfaces, or is it the shared base a real family of such adapters extends? A **port adapter** does — it lives under a folder naming its technical concern (`EventStore/`, `Projection/`, `Messaging/`, `Uniqueness/`...). That folder names the generic role when real plurality of differently-conceived siblings already lives under it (one per BC, same shape); it names the concept instead when it would only ever hold a single, non-repeating cross-cutting feature with no sibling family.
- **Plumbing** is what's left: it implements a vendor's own interface directly, or configures/produces a vendor object, with genuine behavioral coupling and no port of ours behind it — it lives under a folder naming the vendor directly, at `Infrastructure/`'s own root, no invented concern-name hosting it. A vendor shipping several distinct products for the same problem space (Doctrine: DBAL, ORM...) gets one extra level naming which product (`Doctrine/Dbal/`); a vendor owning a single product in its space (Messenger, Sentry, a Patchlevel package) stops at its own name (`Symfony/<component>/`, `Sentry/`, `Patchlevel/<package>/`). Any deeper role-named subfolder earns its own level only when it actually holds more than one file today — a lone file under a lone role folder is promoted straight to its vendor folder instead, dropping every level that adds no real information, checked at that exact location and not by precedent elsewhere in the repo (a folder name legitimately justified by real plurality somewhere else doesn't grant a pass to a spot with none). That promotion itself only holds when the vendor folder's other files already share the same role as the one being promoted — never when it would mix a distinct kind of file into a level otherwise consistently one role, which keeps its own folder instead, even solo.
- A class name doesn't have to read as fully self-explanatory in isolation — the namespace path around it is real information a reader already sees (an import line, an IDE breadcrumb), not decoration, and is allowed to carry part of what disambiguates a bare role name (a bare `TransactionMiddleware` only reads as "which engine's transaction" once `Doctrine\Dbal` is read alongside it). This is what makes dropping a now-redundant word from a class name correct rather than lossy: the word isn't gone, it moved to the path that already carries it.
- A port adapter's class name always prefixes with that vendor's own component name (its actual package/module identity, never the parent company) — no exception, regardless of how many implementations exist today — unless that name shares its lexical root with the folder it lives directly under (both naming the same technique in different words), in which case the parent company's name is used instead, since only that adds information the folder doesn't already give. Either way, the class name mirrors its port's own name (minus `Interface`) — checked against the port's real method contract, never an invented synonym alongside it. Plumbing under its own vendor-named folder needs no such prefix — the folder already says it; a class touching a second vendor besides the one its folder names carries that second vendor's own name too, on the class itself, since the folder covers only the first. A vendor subfolder nested under that same concept folder is warranted only once the adapter needs more than its own bare file — a scoped client, a vendor-shaped exception, a mapping DTO; a single-file adapter with no such sibling stays flat at the concept folder's own root instead, its class-name prefix alone already carrying the vendor identity.
- `EventStore/` and `Projection/` sit directly under `Infrastructure/`, holding the storage/read use cases that configure a port adapter's behavior for a specific model (a Repository, a Publisher, a Finder, a Projector): the former for the write/Domain side, the latter for the read/Application side.
- Event Store repository: `EventStore/<Vendor><Agg>Repository`, `final readonly`, implements `<Agg>RepositoryInterface`; injects `#[Autowire(service: 'event_sourcing.<subdomain>.<bc>.<aggregate>.repository')] Repository<Agg> $repository`; `has()` delegates as-is, `load()` catches `AggregateNotFound` and re-throws its own `<Agg>NotFoundException`; `save()` catches `AggregateAlreadyExists` and re-throws its own `<Agg>AlreadyExistsException` the same way — every aggregate's identity can collide at the event-store level regardless of whether the BC currently relies on it as a business guard, so the adapter always encapsulates it, never a bare delegate.
- Projector: `#[Projector('<subdomain>.<bc>.project_<name>')] final readonly Dbal<X>Projector extends AbstractDbalProjector` (e.g. `sales.order.project_orders`), a `public const string TABLE`, one `#[Subscribe(<Event>::class)] on<Event>()` method per event, and `configureSchema()`. No `_on_<trigger>` clause — a Projector reacts to many events feeding one materialization, so no single trigger to name. A status/type column stores the Application `<X>Status` enum's value, never the Domain `<X>State` enum's — the projection is a read model consumed through a Finder/DM, the same boundary that already forbids the Domain enum crossing into `Application/`/`dm.md`'s exposition surface; deriving the column value from `<X>State` instead couples the stored/filterable value to a representation Domain never promises to keep in sync with `<X>Status`.
- One projection per materialization shape (one table, named after what it materializes); as many Finders as there are read axes over that table. A new Projector is warranted only when the access shape itself differs (key, granularity, denormalization) — never just for a new DTO.
- `<Vendor>IntegrationEventPublisher` (`Shared/Infrastructure/EventStore/`) is the only piece touching the Store for Integration Events, implementing `Shared\Application\IntegrationEvent\IntegrationEventPublisherInterface`'s `publish()`: `Webmozart\Assert::subclassOf($aggregateClass, AggregateRootMetadataAware::class, ...)`, then derives the stream from `<aggregateClass>::metadata()->streamName($id)` with `'integration.'` prepended.
- DBAL Finder: `Dbal<X>Finder extends AbstractDbalFinder<Result>`, `final`, never `readonly` (`filter()` clone-appends to its own `$filters` list) — the same base class serves both a collection/filterable read, consumed via `foreach`/`count()`/`paginate()`, never a terminal `get()`, and a single-shot lookup via `one()`; no separate collection subclass. A single-shot lookup is named `ofX()` when absence is an anomaly: it throws its `<X>ResultNotFoundException` (mapped in `config/packages/exceptions.php`). It's `ofXOrNull(): ?Result` instead when absence is a valid outcome for at least one caller.
- `AbstractDbalFinder` never stores a built `QueryBuilder` — each `filter()` call clone-appends its closure to a list, and every terminal method (`getIterator()`, `one()`, `count()`, `paginate()`) builds a fresh `QueryBuilder` from scratch and replays every stored closure onto it. Cloning a `QueryBuilder` itself deep-clones every bound parameter object, and a bound `\BackedEnum` is never cloneable (a PHP language restriction) — building fresh instead of cloning sidesteps that entirely, on top of skipping Doctrine's own per-clone parameter-object copy.
- Binding a `\BackedEnum` into a query passes the object itself — `Shared\Infrastructure\Doctrine\Dbal\Enum\UnwrapBackedEnumMiddleware` (a Doctrine DBAL Driver Middleware, auto-tagged) unwraps it to its own `->value` at the Statement's `bindValue()`, the single choke point every bound value passes through whether from a plain `setParameter()` or an `ArrayParameterType`-expanded `IN (...)` — never a hand-unwrapped `->value` at the call site, which duplicates what the Middleware already owns.
- A filter binding more than one literal value uses `QueryBuilder::createNamedParameter()` at each call site instead of a hand-invented `:name` plus a matching `setParameter()` call — it returns the placeholder to embed directly in the expression, and the same value reused across several sub-conditions (e.g. one cutoff compared against several columns) calls it once and reuses the returned placeholder, never one invented name per sub-condition for what is the same bound value.
- `QueryBuilder::expr()` is reserved for a condition assembled dynamically — a set of filter blocks added or removed at runtime depending on which input parameters were actually supplied. A condition whose full shape is already fixed and known statically stays a literal SQL string instead, never `expr()` for its own sake.
- A single-shot lookup's or a collection filter's parameter names the CONCEPT it references, never the raw field/carrier name — `of<Concept>`/`by<Concept>`, not `of<Concept>Id`/`by<Concept>Id`, even though the underlying parameter is typed `string $<concept>Id` (a foreign aggregate reference, plain string per `domain.md`). This holds regardless of which shape (`of*` exact lookup, `by*` collection filter) is doing the naming — the two must never diverge on the same principle. The exception is a bare own-identity lookup (`ofId`) where there is no foreign concept to substitute, and a field whose own real domain term happens to already end in "Id" as part of that term itself (e.g. a VO literally named `KeyId`, not a generic "Key" reference decorated with an "Id" suffix) — that case keeps the term whole (`ofKeyId`), since dropping the suffix there would invent a word nobody uses, not name the concept more precisely.
- A collection Finder's dynamic filter is `by<Concept>(string $value): static` — a single equality parameter by default. It becomes variadic (`by<Concept>(string ...$values): static`, `IN` instead of `=`) only once a real caller actually needs to filter by more than one value at a time — never speculatively, since a single-value `IN` optimizes identically to `=` and an unused variadic parameter is dead flexibility. A non-equality operator appends one suffix from this exhaustive list, never an improvised one: `Not` (`!=`/`NOT IN`), `Containing`/`StartingWith`/`EndingWith` (`LIKE`), `After`/`GreaterThan` and `Before`/`LessThan` (`>`/`<`, date vs numeric field), `AfterOrEqual`/`GreaterThanOrEqual` and `BeforeOrEqual`/`LessThanOrEqual` (`>=`/`<=`). `Not` always precedes any other suffix when composed (`byNameNotContaining`, never the reverse) and never attaches to a bare predicate. A boolean or nullity check with one meaningful polarity is a bare nullary predicate instead (`active()`, `untracked()`) — the opposite polarity, if ever needed, gets its own separately-named method, never a `Not` suffix on this one. An `OR` across exactly two columns fuses both names in alphabetical order (`byEmailOrName`, not `byNameOrEmail`); across three or more, abandon concatenation for an intent-named method instead (`matching(string $term)`). Sorting is `sortedBy<Field>(): static` — same chainable shape, but it orders rather than narrows.
- One `Dbal<X>Finder` per materialization shape (same table, same `Result`) — a new implementation is warranted only when the shape itself differs, same threshold as the Projector rule above.
- A collection Finder's `buildBaseQuery()` ends on an explicit `orderBy(<its own id column>, 'ASC')` — a bare `SELECT` with no order gives pagination no stable, deterministic slice across two calls. Since a root-generated aggregate id (`UuidTrait`, `uuid7`) is time-ordered, ordering by id alone already gives a chronologically-consistent default with no dedicated column needed. An aggregate whose id is instead derived (`DerivedUuidTrait`, `uuid5` on a parent's id — no time component at all) breaks that assumption: its Finder orders by its own creation-date column first, with the id as an `addOrderBy()` tiebreaker (`orderBy(<creation-date column>, 'ASC').addOrderBy(<id column>, 'ASC')`) instead — the tiebreaker only matters for two rows sharing the same creation instant, since the derived id itself carries no usable order of its own. A `sortedByX()` method is introduced only once a real exposition need calls for a different order.
- Reaching a vendor is two levels, both named after the business concept, never a generic `Gateway/` bucket: the port is `<Bc>/Application/<Concept>/<X>GatewayInterface`, its adapter `<Bc>/Infrastructure/<Concept>/<Vendor>/<Vendor><X>Gateway implements <X>GatewayInterface`. That same folder is the only holder of the scoped HTTP client, `<Vendor>Client` — speaks the vendor's protocol. A Gateway with no need to classify its own failure for retry purposes turns transport/decoding failures into a single `<Vendor>ClientException`, one fixed class per vendor with every failure shape folded into its own named constructor, never a growing family of sibling classes the way a BC's own `Domain/Exception/`/`Application/Exception/` is — that exception sits bare beside the client and the Gateway, never under its own nested `Exception/`. A Gateway whose failure DOES need retry/poison-pill classification (a `#[Policy]`/`#[Processor]` subscriber calling it needs to tell a fatal failure from a transient one) skips the `<Vendor>ClientException` layer entirely instead: the Client throws the Application-owned concrete failure type directly (e.g. `<X>TransientFailureException`/`<X>FatalFailureException`, both extending the Port's own abstract `<X>GatewayException`) — no vendor-named exception class exists at all in that case, the vendor-specific detail lives only in the thrown message, never in a dedicated class. The client moves to `Shared/Infrastructure/Gateway/<Vendor>/` only once a second BC actually consumes the same vendor, never in anticipation of one. This split is earned the same way as any other port adapter's own vendor subfolder: once the integration needs more than the bare Gateway file — a scoped client, its own typed exception, a mapping DTO. A Gateway fully delegating to another abstraction with no client or exception of its own stays flat at its concept folder's own root instead, its class-name prefix alone carrying the vendor identity. The concept segment names each Bounded Context's own real Ubiquitous Language term for that integration — a process noun in one BC and a role noun in another are both legitimate when that's genuinely how each domain's own practitioners speak, never forced onto one shared grammatical axis across BCs for symmetry's sake alone.
- A composite projection subscribes to its own Domain Events plus a foreign BC's Integration Events — never a foreign Domain Event, never another BC's projection. It reads the foreign stream directly at fold time to denormalize onto its own table — `Projection/Reducer/Stream<X>Reducer`, reading via `Store::load(new Criteria(new StreamCriterion($streamId)))`, folded with `Patchlevel\EventSourcing\Message\Reducer` (`initState()`/`when()`/`reduce()`), converted to a small immutable DTO. Each foreign attribute that can change over time gets its own `#[Subscribe(<IntegrationEvent>)]` fan-out method, materialized as a nullable column. A Policy mutates (dispatches a Command); a Reducer only reads.
- A nested role folder under `EventStore/`/`Projection/` (`Reducer/`, or any other) only earns its own level once real plurality lives under it — the `Stream` prefix on a class distinguishes a fold over the event stream from a sibling case built over already-materialized data, and comes first (`Stream<X>Reducer`, matching `Dbal<X>Finder`/`<Vendor><X>Gateway`'s own mechanism-first ordering), never as an infix.
- A cross-BC provider contract, or several same-BC implementations of one strategy interface a router delegates to, is wired as a tagged iterator — never `#[AutoconfigureTag]`/`#[AutowireIterator]` inline attributes, which put an Application-layer class under a direct dependency on an Infrastructure vendor token. The interface itself carries no attribute; the owning `config/services/<subdomain>.php` tags every implementation (`$services->instanceof(<X>Interface::class)->tag('<tag>')`) and binds the consumer's constructor arg (`$services->get(<Consumer>::class)->arg('$x', tagged_iterator('<tag>'))`). The `instanceof()` call must be declared *before* `SubdomainServiceLoader::load()` in that same file — declared after, the tag silently never applies to any already-loaded definition.
- A cross-BC gate on the bus (a fact one BC owns that any Command/Query across every BC must respect) is a Messenger middleware living in the owning BC's own `Infrastructure/<Concern>/`, registered in `config/packages/messenger.php`'s `middleware` array on whichever bus needs it, reading that BC's own Finder directly — never a `Shared`-owned middleware reaching into a business BC. The message opts in through a pure marker interface in `Shared\Application\Command\`/`Query\` naming the field the gate checks — a zero-field contract only, so a Command/Query implementing it stays within its own "native types only" boundary rule.
- A business time threshold that is a genuine operational knob (a deployment might retune it, no Domain-side invariant depends on its exact value) is a container parameter under `config/services/<subdomain>.php` (`<subdomain>.<x>_window_days` looking back, `<subdomain>.<x>_days_ahead` looking forward) — never a literal in code. It's bound into the service that computes the date via that same config file's explicit `arg()` call when the service is Application-layer (a Handler never carries a Symfony-DI attribute, same reasoning as the tagged-iterator rule above), or via `#[Autowire(param:)]` directly on the constructor when the service is Infrastructure-layer. A threshold that is itself an aggregate's own invariant (`domain.md`'s Domain-owned `private const`) is never re-expressed as a second, container-injected value — Application reads that same const directly at its call site (e.g. computing a Finder cutoff), since Domain is the value's only source of truth and re-injecting it would let the two drift apart.
- A critical section whose duplicate execution would trigger a real external side effect (not just re-checking an aggregate's own guard) is wrapped in `Shared\Infrastructure\Locking\LockingTrait::withLock()`, keyed by a resource name scoped to the specific entity being protected. Applied via a `#[AsDecorator]` around the port it protects, never inlined into that port's own implementation, so the port itself stays substitutable and free of locking concerns. The lock's own failure (`LockNotAcquiredException`) is caught at that same decorator boundary and re-thrown as the caller-facing business exception — it stays unmapped in `config/packages/exceptions.php` so a caller that forgets to catch it surfaces as a raw 500 instead of a silently swallowed refusal.

## Tests

### Conventions

#### Naming
- Repository: success `it*`, failure `itThrowsWhen*`.
- Projector: `itProjectsOn*` for every reaction that inserts a new row or mutates an already-projected one in place (no dedicated failure shape). A reaction whose own assertion proves the row is gone (a `fetchRow()` returning nothing/false), not merely updated, is `itRemovesOn*` instead — the verb states what the row's own final state actually is, never a euphemism for a real deletion. No noun between the verb and "On" — the event named after it already carries what's affected. The event name that follows "On" is always the event's own full class name, own-aggregate or foreign alike — unlike an `#[Apply]` method (a purely mechanical dispatch hook, safe to shorten since it's never read as a sentence), a test method name is read as a description, and a truncated event name (dropping its own aggregate prefix) stops reading as a real, recognizable proper noun.
- Finder: an exact lookup that throws when absent is `itGets*`, failure `itThrowsWhen*`. A lookup that stays nullable instead is named `itFinds*`, covering both outcomes in one method — for that one, absence is a valid result, not a failure, so `itFinds*` never takes the `itThrowsWhen*` shape. A collection read (iterate/filter/paginate) is `itLists*`/`itFilters*By*`/`itPaginates*` — `itGets*`/`itFinds*` are reserved for a single-shot lookup, never a collection scan.
- A single-shot lookup's own `itThrowsWhen*` names the lookup parameter (`WhenIdNotFound`, `WhenTrackingReferenceNotFound`...), even for the bare own-identity case (the `ofId` exception in the naming rule above carries through to its test name too) — a Finder can expose more than one lookup axis in the same test class, so the parameter name is what keeps them distinguishable.

#### Structure
- A Finder test orders its methods by shape, never by declaration order in the interface or by whim: every single-shot lookup (`itGets*`/`itFinds*`, success then its own `itThrowsWhen*`) first, every collection filter (`itFilters*By*`) next, every bare collection read (`itLists*`) after that, every `itPaginates*` last. A Finder exposing only one of these shapes keeps that shape's own internal order (success before failure) — the cross-shape ordering only applies once two or more shapes coexist in the same test class.
- A Finder never rewrites the mechanical iteration battery per aggregate — a Finder implementing `IterableFinderInterface` extends `Shared\Tests\Support\TestCase\AbstractIterableFinderTestCase` instead, which owns `itLists`/`itListsWhenEmpty`/`itCounts`/`itIndexes` generically through methods the concrete test implements: `finder()` (resolves its own real Finder), `seed(int $count): list<string>` (builds and stores that many rows, returning their ids in the Finder's own real order), and `idOf(object $result): string` (reads the id off its own Result type). A Finder implementing `PaginatableFinderInterface` additionally composes `Shared\Tests\Support\PaginationTrait` — never a second base class, since the two Shared interfaces are independent and a class hierarchy would force one onto a Finder that never implements the other. The concrete test writes its own `itPaginates`/`itPaginatesWhenEmpty`, calling the trait's `traversePages()`/`traverseEmptyPage()` for the mechanic — same shape as a Query Handler's own pagination test (`application.md`). The base class proves `IterableFinderInterface`'s own contract, never a synthetic double — each real concrete Finder's own test is the sole proof, no standalone test of the base class exists. It lives under `Support/TestCase/`, never mirroring `src/Shared/Application/Finder/`. The concrete test then adds only what's genuinely its own — single-shot lookups, filters, their own failure shapes, and its own pagination test.
- A collection filter/list/paginate test asserts only which items matched (their id, or the field the filter itself keys on) — never the full Result shape a moment already exercises its own lookup on. The single-shot lookup (`itGets*`/`itFinds*`) is where every field gets verified once; repeating that in a filter/list/paginate test only duplicates coverage and adds nothing a mutant on an unrelated field would catch there instead. This holds only once such a lookup genuinely exists on that same Finder — a collection-only Finder with no single-shot counterpart keeps full-shape assertions on its own filter test instead, wherever one exists. A Finder with neither a single-shot lookup nor a filter gets its own dedicated hydration test (every Result field, on one seeded item) alongside the inherited id-only `itLists`/`itPaginates`, since nothing else would ever verify the shape.
- A Projector test asserts DB state through a `private fetchRow(string $id): array|false` helper — never an inline `SELECT`. A row whose only check is presence/absence (`assertFalse`/`assertNotFalse`) calls `fetchRow()` straight inside that assertion; a row whose own fields also get read is assigned to a variable first instead.
- A Projector test exercising an UPDATE (a reaction on an aggregate that already has a projected row) stores a second, unrelated row (different id and a different value on the field the UPDATE writes) alongside the one under test, and asserts that row stayed untouched — a single-row dataset can't distinguish "the right row was targeted" from "whatever row existed got updated", so a mutant removing the UPDATE's WHERE/identifying criteria entirely survives unnoticed.
- `// Then` assertions on the subject's own row and the decoy's own row are grouped by row, not interleaved — every assertion on the subject's row (its own `fetchRow()` call, its own `assertNotFalse`, every field check) together first, then the decoy's own row the same way, never a shared `assertNotFalse($row); assertNotFalse($otherRow);` pair followed by each row's own field checks scattered after.
- A decoy with no cascading Integration Event reaction of its own is store()-ed on its own line in `// Given`, never bundled into the subject's own `store()` call — `// When` keeps exactly the one `store()` that actually triggers the reaction under test. A `store()` call combining a decoy and a subject whose own transition cascades an Integration Event reaction onto another aggregate's already-projected row (an UPDATE/DELETE keyed by id) is the one exception: it needs that referenced row's own aggregate built and store()-ordered before the cascading aggregate for both the decoy and the subject alike — a decoy given the same cascading transition as the subject (e.g. a suspended control in a reactivation test) follows the identical referenced-first ordering, not just the subject.

#### Test doubles
- An Application-level test (a Policy/Handler exercising the port) doubles the port interface directly, no HTTP involved. Only the dedicated Infrastructure test for the concrete adapter doubles the vendor client instead, to exercise that adapter's own HTTP↔Domain mapping (payload serialization, error mapping to its own client exception).
