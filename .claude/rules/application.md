## Source

### Rules

**ALWAYS**
- One folder per message: `Application/{Command,Query}/<Name>/` = `<Name>.php` + `<Name>Handler.php` (+ `<Name>Result.php` for a Query). The `Handler.php` suffix is mandatory — `SubdomainServiceLoader`'s glob silently skips anything else.
- A Query reads through an `Application/Finder/<Aggregate>/<X>FinderInterface` (with its `<X>Result` co-located), never through a Repository. A Command writes through a Repository (Domain); it may also read through a Finder if it needs to. A Finder parameter's type follows CQRS's own read/write model separation: never a Domain-owned Value Object or identity type (it carries write-side invariant-enforcement behavior — accepting it in a Finder recouples the read model to the write model the pattern deliberately keeps independent), but a `\DateTimeImmutable` or an `Application/Status/<X>Status` enum is fine as-is — neither carries write-side behavior (a bare date has no domain invariant of its own, and `<X>Status` already belongs to the read side, decoupled from `<X>State` by definition), so passing it through doesn't recouple anything.
- A side effect reacting to an event (`#[Policy]`, whether the event is a Domain Event from the same BC or an Integration Event from another) carries zero business logic: it either dispatches a Command, calls an outbound port directly, or enriches by reading a Repository — never a Finder. It dispatches at most one Command per invocation — a multi-item side effect (a collection scan, a fan-out) belongs in that Command's own Handler instead, never inline in the Policy.
- An outbound call — mutating or read-only — never belongs in a Command handler: it always runs inside an open database transaction, holding it hostage to network latency regardless of what the call itself does; and once the handler's own Command is routed async, a transport retry on failure re-fires that same external call on every attempt. A call reacting to an already-recorded fact belongs to a Policy instead — inside a transition, the aggregate's invariant would otherwise be checked after the call has already left, and the failure of a third party would roll back a decision that was already ours to keep, the outcome carried by a second Command. A call gathering external facts before any decision is made belongs to a Driving Port instead — it resolves the external state first, decides, then dispatches a Command that already carries a settled outcome.
- Acting on many items (a DM scanning for eligible ones, a Handler cascading to related aggregates) dispatches one Command per item through the Command bus, routed `async` in `messenger.php` — never mutated inline in a shared loop. Async is what actually isolates each item (its own transport message, its own transaction); a synchronous nested dispatch shares the caller's transaction, so one item's rollback poisons every sibling already processed in the same loop.

**NEVER**
- Put a non-native-type field on an Integration Event.
- Add `#[OnFailed]` to a Publisher's subscriber — a failed publish must halt the subscription, not skip silently.
- Pre-check a condition the target aggregate's transition method already guards — call it unconditionally, let the aggregate decide (Tell, Don't Ask). A `has(id)` fast-path before constructing a brand-new aggregate is not this: it's a technical redelivery guard on a creation command, not a re-check of a business rule the aggregate owns — the actual duplicate-creation race is still closed by catching the store's own already-exists rejection around `save()`, never by trusting that pre-check alone.
- Load another Bounded Context's Repository, or dispatch into its Command bus, to check or gate on its state — a same-BC cross-aggregate invariant loads the sibling aggregate through its own Repository and calls its `ensure*()` guard (`domain.md`); a cross-BC invariant never synchronously reaches into the other BC at all. A point-in-time check reads a local Finder kept current by that BC's own Integration Events (a Projector already listening); a continuously-held invariant reacts to the Integration Event via a `#[Policy]`, which mutates local state. When that mutation can lose a race against state committed after the triggering fact (the source aggregate moved on before the local reaction landed), the Policy catches its own aggregate's rejection and dispatches a compensating Command instead of letting the exception bubble — never a synchronous cross-BC call to resolve the conflict on the spot.
- Route a Command `async` in `messenger.php` for a reason other than the many-items isolation above. A `#[Policy]` reacting to a single event and dispatching a single Command needs no extra routing on that account — the Policy's own execution is already the isolation boundary; the Command it dispatches only needs `async` if some *other* call site also dispatches it inside a many-items loop.

### Conventions
- An application failure is a `final` exception extending `\RuntimeException`, implementing `Shared\Application\Exception\ApplicationExceptionInterface`; named static factory (`forId`, `forIdentifier`...). A failure shape common to every BC is the `abstract` `Shared\Application\Exception\ResultNotFoundException`, mapped once in `config/packages/exceptions.php`; each BC's concrete `final` exception extends it under its own `Application/Exception/`, with its own named factories.
- A check depending on a fact about the outside world (can turn out differently tomorrow for the same candidate, without the candidate itself changing) is a Gateway, resolved by the Handler before it ever dispatches to the aggregate — never injected into a transition. Its own failure is an application exception, not a Domain one, even when the aggregate would otherwise have thrown for a related reason on the same call.
- An Application port meant to be called directly by a Delivery Mechanism (bypassing the Command/Query bus) is marked `#[DrivingPort]` (`Shared\Application\Port`) — a pure marker read by phpat, zero DI effect. The data crossing that boundary is `CommandInterface`, `QueryInterface`, a class named `*Result` under `Application/`, `ApplicationExceptionInterface`, `\DomainException` (generic or a concrete Domain exception), a named return type declared by any `#[DrivingPort]` interface's own method, a validation compound (`extends Compound`), or an `Application/Status/<X>Status` enum. `<X>Status` never proxies its Domain `<X>State` enum's case values — the two are separate value spaces that may diverge (a read/UI-facing status is not guaranteed the same shape as the write-side state it's read from). It may carry the same pure identity predicates as its Domain enum (`self::CASE === $this`) for a DM to gate a UI hint — never a transition/precedence rule, Domain-only.
- A `#[DrivingPort]` interface's own implementation lives beside it under `Application/<Concept>/` when it dispatches a Command or guards a business rule (a domain-state conditional, a business-named exception) — the port and its content both sit at the core, only the Delivery Mechanism calling it is the actual adapter. It moves to `Infrastructure/<Concept>/` once it's pure technical delegation with no business branching of its own.
- A validation compound (`Application/Validation/Valid<Name> extends Compound`) lists the Symfony `Assert` rules that carry the user-facing message, then closes on `ValidValueObject(<Vo>::class)` as a net. The Value Object keeps the last word; the asserts exist so the client reads *why* the field is refused rather than that the domain refused it. Wrap the list in `Assert\Sequentially` whenever a single bad input can trip more than one of its own rules at once (e.g. a blank value failing both a not-blank rule and a closed-vocabulary rule) — otherwise the client sees several redundant violations for one mistake, and the closing net still fires on top of an already-explained field-level failure. A flat, unwrapped list stays correct only when every rule in it targets a genuinely different failure shape with no overlap.
- A uniqueness check reuses the generic `Shared\Application\Validation\ValidUniqueValue` constraint through a thin per-context compound (`Application/Validation/ValidUnique<Name> extends Compound`) supplying only the discriminator (a `\BackedEnum` case) and, when needed, the composite scope or the property path excluding the record being edited — it never re-implements the registry lookup itself, `ValidUniqueValue`'s own validator stays the single owner of that logic.
- An Integration Event lives in `Application/IntegrationEvent/<Event>/<Event>IntegrationEvent`, co-located with its own Publisher, suffixed `*IntegrationEvent`, is `final readonly`, implements `IntegrationEventInterface`; named `#[Event('integration.<subdomain>.<bc>.<aggregate>.<verb>')]` — a leading `integration` segment, i.e. its Domain Event's own id prefixed by `integration.`, since it marks a visibility/routing boundary rather than a technical detail. Tagged `#[SensitiveData]`/`#[DataSubjectId]` when it carries personal data.
- A Publisher lives in `Application/IntegrationEvent/<Event>/<Event>Publisher`, `final readonly`, `#[Publisher('<subdomain>.<bc>.publish_<event>')]` — never its own class-name-derived suffix, and no `_on_` trigger clause: a Publisher's target and trigger are the same fact by construction (co-located, same event name), so naming both would repeat the same word. It is invokable: `#[Subscribe(<DomainEvent>::class)]` sits on `__invoke()`, one Publisher for one event, injecting `IntegrationEventPublisherInterface` (plus a Repository when the Integration Event needs data beyond the triggering Domain Event's own payload) and calling `$this->publisher->publish(<Aggregate>::class, <id>, new <Event>IntegrationEvent(...))`.
- A side-effect reaction lives in `Application/Policy/<Action>On<Event>`, named `#[Policy('<subdomain>.<bc>.<action>_on_<event>')]` — snake_case of its own class name. It is invokable: `#[Subscribe(<Event>::class)]` sits on `__invoke()`, one reaction for one event, where a Projector carries one `on<Event>()` per event instead.
- A Policy that creates an aggregate derives the identity from the triggering event (`uuid5` on a bound namespace) and its handler returns early when that aggregate already exists — otherwise a replay opens a duplicate.
- A Policy needing data from an aggregate that an independent reaction to the same triggering event could erase races that reaction — nothing orders two subscriptions relative to each other. It resolves what it needs from the triggering event itself or a deterministically-derived id instead of re-loading a value erasure could already have shredded.
- A Query's class documents its return contract: `@implements QueryInterface<TResult>` (otherwise `ask()` only returns `mixed`). Its return shape is one of: `PaginatedResult<X>` (paginated), `StreamResult<X>` (streamed, for volume), `list<X>` (all), `?XResult` (one or none), `XResult` (exactly one).
- A Command/Query name referencing another aggregate names the concept (`By<Concept>`, `For<Concept>`), never its carrier field (`By<Concept>Id`) — the constructor argument itself stays `<concept>Id`.
- A Service holds pure logic (zero I/O) or extracts steps of a use case: inject it as the concrete class plus bound scalars. An interface is reserved for an actual I/O boundary (substitution/stub in tests).
- A presence/freshness check against a Read Model (a Finder/Result field null, a claimed value vs. its current counterpart) is an applicative pre-condition, not a Domain rule — it stays inline in the Handler, throwing its Application exception directly. It never gets wrapped in a Domain Service/Domain exception pair for the sole purpose of relocating the `if`: a Domain Service earns its place by owning a Write Model invariant (an Aggregate's own nullary invariant guard) or by holding logic a Value Object's own comparison already expresses — not by re-hosting a null check or a bare `$vo->equals()` call read off a Result.

## Tests

### Conventions

#### Structure
- A validation compound is exercised through `CompoundConstraintTestCase`, one data set per refused value, naming the rules it trips — the assertion compares the whole ordered list, so a rule dropped from the compound makes its data set fail. A value that trips the closing `ValidValueObject` alone is a missing `Assert`: the message the client gets is the Value Object's, not the field's.

#### Naming
- Command Handler: success `it*`, failure `itFailsWhen*` — a no-op success (idempotent re-dispatch) is `itIgnores*`, exercising the exact same aggregate self-guard as `itDoesNot*` one altitude up (through the real `dispatch()`, never pre-guarded — Tell, Don't Ask) — never `itDoesNot*` itself, that name stays reserved for the isolated Domain Aggregate test. A refusal the aggregate itself records as its own dedicated event (neither a silent no-op nor an exception) is `itRejects*`, mirroring the same transition's own Domain Aggregate test.
- Query Handler: success `itGets*` / `itLists*` / `itLists*By*` / `itPaginates*`, failure `itFailsWhen*`.
- Side effect (`#[Policy]`): `it<Verb>`, bare — same shape as a Publisher's own test, the class already names the event and the object acted on, no dedicated failure shape. A guard branching on the triggering item's absence gets its own negative control, `itIgnoresWhen*`, the same idiom as a Command Handler's no-op, never `itDoesNothingWhen*` — `itDoesNot*` stays reserved for the isolated Domain Aggregate test. No such guard, no negative control. A noun the class name already fixes is never repeated inside the method name, success or negative-control alike — only a distinct concept earns its own word.
- Publisher: `itPublishes`, bare — one test method per class since the class itself already names the event, no dedicated failure shape.
- Validation compound (`CompoundConstraintTestCase`): success `itAccepts`, failure `itRefuses` (one data set per refused value, per the Structure convention above).
- A `<X>Status`'s own boolean predicate, exercised by iterating every case in one test: `it{Predicate}` (mirrors the method name, e.g. `itIsActive` for `isActive()`) — never a trailing `OnlyWhen<CurrentCase>` naming today's exact case set as if it were the contract; a later case satisfying the same predicate would make that name wrong without the predicate itself having changed meaning.
