## Source

### Rules

**ALWAYS**
- One folder per message: `Application/{Command,Query}/<Name>/` = `<Name>.php` + `<Name>Handler.php` (+ `<Name>Result.php` for a Query). `Handler.php` suffix is mandatory — `SubdomainServiceLoader`'s glob skips anything else.
- A Query reads through `Application/Finder/<Aggregate>/<X>FinderInterface` (co-located `<X>Result`), never a Repository. A Command writes through a Repository; may also read through a Finder. A Finder parameter is never a Domain-owned VO/identity type (recouples the read model to the write model); `\DateTimeImmutable`/`Application/<X>Status` are fine as-is.
- A Command/Query/Integration Event constructor field is never a Domain-owned VO/identity type. `\DateTimeImmutable`/backed enum are fine typed as-is, crossing their own transport's native normalization — never pre-formatted to a string and re-parsed.
- A side effect reacting to an event (same-BC Domain Event or foreign Integration Event) is `#[Policy]` only when its action carries real business meaning of its own (a Command meaningful on its own, a business-facing outbound port call); a reaction with no business meaning at all (technical/infrastructure, nothing a domain expert would name as a capability) is `#[Processor]` instead (`Shared\Infrastructure\Processor`, under `Infrastructure/<Concept>/`, injecting the vendor/technical mechanism directly), never `#[Policy]`. A `#[Policy]` carries zero business logic: dispatches a Command, calls an outbound port, or enriches by reading a Repository. Acting on more than one item reads a Finder directly and repeats the single action once per item — one Command dispatch each (`async` in `messenger.php` only when per-item isolation matters) or one port call each. Never an intermediate wrapper Command whose Handler exists only to scan-and-repeat — that's pure mechanism, never a named capability, regardless of what the per-item action is.
- A `#[Policy]`/`#[Processor]` calling an outbound port may carry `#[OnFailed]`, acting only once the vendor's own retry budget is exhausted — never substituting for the retry. It distinguishes fatal (retrying can never succeed) from transient (always rethrows, ordinary poison-pill): fatal dispatches a Command recording what happened, never a bare log with nothing else.
- An outbound call, mutating or read-only, never belongs in a Command handler — it runs inside the open transaction, and an async-routed handler re-fires it on every transport retry. A call reacting to an already-recorded fact belongs to a Policy instead, outcome carried by a second Command. A call gathering external facts before a decision belongs to a Driving Port instead — resolve, decide, then dispatch a Command with the settled outcome.
- Acting on many items (a DM scan, a Handler cascade) dispatches one Command per item through the bus, routed `async` — never mutated inline in a shared loop. A synchronous nested dispatch shares the caller's transaction; one item's rollback poisons every sibling already processed.

**NEVER**
- Put a Domain-owned VO/identity type field on an Integration Event.
- Add `#[OnFailed]` to a Publisher's subscriber — a failed publish must halt the subscription, not skip silently.
- Pre-check a condition the target aggregate's transition already guards — call it unconditionally (Tell, Don't Ask). Same for a `has(id)` fast-path before creating a brand-new aggregate: between that read and `save()`, a concurrent attempt can land in between (TOCTOU) — the check adds a second code path with no correctness value. The store's own already-exists rejection around `save()`, turned into a silent no-op, is the only mechanism that closes the race — `has(id)` in front of it is never load-bearing, never added.
- Skip the `save()` catch on any creation Handler whose id is deterministic (DM-supplied or `for<Concept>()`-derived) — every such creation path faces at least one of: Policy redelivery (position persisted only at batch-level flush, a crash between `save()` and flush replays the message), async-transport redelivery (worker crash before ack), or plain request concurrency (double submit, two tabs, client retry — even on a purely synchronous DM path). No creation path is exempt from all three by default. The catch itself is implemented once, at the Repository (`infrastructure.md`: `save()` catches `AggregateAlreadyExists`, re-throws the BC's own `<Agg>AlreadyExistsException`) — this rule only decides whether that mechanism protects a given Handler, and whether the Handler's `@throws` names it; it never means hand-adding a catch inside the Handler itself.
- This `has(id)` ban is specific to guarding a *creation* — never `has(id)`/`!has(id)` guarding a `load()` or a dispatch on an aggregate that may legitimately not exist yet (a Policy racing ahead of the aggregate it targets). That's a routine business check with no atomic substitute: `load()` has no graceful not-found return, so skipping would let `NotFoundException` bubble as a subscription error for a valid "nothing to act on yet" outcome. `try { load() } catch (NotFoundException) {}` isn't better — no race is being closed, skipping is correct regardless of timing. This one stays a `has(id)` check.
- Load another BC's Repository, or dispatch into its Command bus, to check/gate on its state — same-BC or not, never load a sibling aggregate from a Handler to ask it a question before a separate transition: two independent Repository loads share no concurrency control. A point-in-time check reads a local Finder instead (kept current by a Projector on the source BC's Integration Events, or the sibling's own Projector same-BC). A continuously-held cross-BC invariant reacts via `#[Policy]` mutating local state; a mutation that can lose a race catches its own aggregate's rejection and dispatches a compensating Command — never a synchronous cross-BC call. An invariant that must hold exactly at transition time, same-BC, shares one aggregate/stream instead.
- Route a Command `async` for a reason other than many-items isolation. A `#[Policy]` reacting to a single event needs no extra routing on that account — its own execution is already the isolation boundary; the Command it dispatches only needs `async` if some *other* call site also dispatches it inside a many-items loop.

### Conventions
- Application failure: `final` exception extends `\RuntimeException`, implements `ApplicationExceptionInterface`; named static factory. Co-located with the component that raises it (`Application/Command/<UseCase>/Exception/`, `Application/Finder/<Aggregate>/Exception/`...), never a flat BC-wide `Application/Exception/`. A shape common to every BC: `abstract Shared\Application\Finder\Exception\ResultNotFoundException`, mapped once; each BC's `final` concrete extends it, co-located. Same co-location inside `Shared` itself (`Finder/Exception/`, `Uniqueness/Exception/`...); only the BC-agnostic marker interface stays flat. Flat `Application/Exception/` is valid only for a genuinely BC-wide abstract/interface root shared by 2+ unrelated components — never a concrete exception.
- A check depending on an outside-world fact is a Gateway, resolved by the Handler before dispatching to the aggregate — never injected into a transition. Its failure is an application exception, even when the aggregate would otherwise throw for a related reason.
- An Application port meant for direct DM calls (bypassing the bus) is `#[DrivingPort]` (`Shared\Application\DrivingPort`, a pure marker). Crossing data: `CommandInterface`, `QueryInterface`, an `Application/*Result` class, `ApplicationExceptionInterface`, `\DomainException`, a `#[DrivingPort]` method's own named return type, a validation compound, or `Application/<X>Status`. `<X>Status` never proxies its Domain `<X>State`'s case values. It may carry the same identity predicates as its Domain enum for a UI hint — never a transition/precedence rule.
- A `#[DrivingPort]` implementation lives beside it under `Application/<Concept>/` when it dispatches a Command or guards a business rule; moves to `Infrastructure/<Concept>/` once it's pure technical delegation with no business branching.
- A method's own `@throws` names every concrete exception its body produces directly (an inline guard, its own Finder/Repository call, its own outbound port call), plus the generic Application/Domain pair for whatever only a bus dispatch can produce from there. A side-effect reaction invoked only through the bus (never directly by a DM/other caller) declares the generic pair alone, even where it also guards/reads directly.
- Inside `Application/<Concept>/`, two classes connect only when one directly constructs/injects the other — never through a driven port or bus interface. A driven port's own interface, and any status/DTO for its vendor-facing shape, stays bare at `<Concept>/`'s own root. Every other maximal group sharing a direct construction edge gets its own named subfolder, even alone. No shared edge anywhere → stays flat.
- Validation compound (`Application/Validation/Valid<Name> extends Compound`): lists `Assert` rules carrying the user-facing message, closes on `ValidValueObject(<Vo>::class)` as a net. Wrap in `Assert\Sequentially` whenever one bad input can trip more than one rule at once. A flat unwrapped list is correct only when every rule targets a genuinely different failure shape.
- A uniqueness check reuses `Shared\Application\Validation\ValidUniqueValue` through a thin per-context compound (`ValidUnique<Name> extends Compound`) supplying only the discriminator (`\BackedEnum` case) and, when needed, the composite scope/excluded-record path — never re-implementing the registry lookup.
- Integration Event: `Application/IntegrationEvent/<Event>/<Event>IntegrationEvent`, co-located with its Publisher, suffixed `*IntegrationEvent`, `final readonly`, implements `IntegrationEventInterface`; `#[Event('integration.<subdomain>.<bc>.<aggregate>.<verb>')]` — its Domain Event's own id prefixed `integration.`. Tagged `#[SensitiveData]`/`#[DataSubjectId]` when it carries personal data.
- Publisher: `Application/IntegrationEvent/<Event>/<Event>Publisher`, `final readonly`, `#[Publisher('<subdomain>.<bc>.publish_<event>')]` — no `_on_` clause (target/trigger are the same fact by construction). Invokable: `#[Subscribe(<DomainEvent>::class)]` on `__invoke()`, one Publisher per event, injecting `IntegrationEventPublisherInterface` (plus a Repository when the event needs data beyond the trigger's own payload), calling `publisher->publish(<Aggregate>::class, <id>, new <Event>IntegrationEvent(...))`.
- Side-effect reaction: `Application/Policy/<Action>On<Event>`, `#[Policy('<subdomain>.<bc>.<action>_on_<event>')]` (snake_case of the class name). Invokable: `#[Subscribe(<Event>::class)]` on `__invoke()`, one reaction per event (a Projector carries one `on<Event>()` per event instead).
- A Policy creating an aggregate derives the identity from the triggering event (`uuid5` on a bound namespace); its handler returns early when that aggregate already exists — otherwise a replay opens a duplicate.
- A Policy needing data from an aggregate an independent reaction to the same event could erase resolves it from the triggering event itself or a deterministically-derived id — never re-loads a value erasure could already have shredded (nothing orders two subscriptions relative to each other).
- A Query's class documents `@implements QueryInterface<TResult>`. Return shape: `PaginatedResult<X>`, `StreamResult<X>`, `list<X>`, `?XResult`, `XResult`. Class name prefixed by the verb the shape implies — `Get<X>` for a single-shot, `List<X>` for a collection shape.
- A Command/Query name referencing another aggregate names the concept (`By<Concept>`, `For<Concept>`), never its carrier field (`By<Concept>Id`) — the constructor argument itself stays `<concept>Id`.
- A Service holds pure logic (zero I/O) or extracts use-case steps: inject as the concrete class plus bound scalars. An interface is reserved for an actual I/O boundary.
- A presence/freshness check against a Read Model is an applicative pre-condition, not a Domain rule — stays inline in the Handler, throws its Application exception directly. Never wrapped in a Domain Service/Domain exception pair just to relocate the `if`.
- A folder holding solely one file of the same name is promoted to its parent's level, dropped entirely — unless the parent's existing files don't already share that file's role, in which case it keeps its own folder even alone.

## Tests

### Conventions

#### Structure
- A validation compound is exercised through `CompoundConstraintTestCase`, one data set per refused value, naming the rules it trips — the assertion compares the whole ordered list, so a rule dropped from the compound makes its data set fail. A value that trips the closing `ValidValueObject` alone is a missing `Assert`: the message the client gets is the Value Object's, not the field's.

#### Naming
- Command Handler: success `it*`, failure `itFailsWhen*` — a no-op success (idempotent re-dispatch, or any guard the aggregate resolves internally with no exception and no observable Read Model/response change) is `itIgnores*`, exercising the same aggregate self-guard as `itDoesNot*` one altitude up (through the real `dispatch()`, never pre-guarded) — never `itDoesNot*` itself, reserved for the isolated Domain Aggregate test. `itRejects*` is reserved for a Handler-tier refusal with its own Handler-observable signal (a distinct exception type, or a Read Model/response difference) — an aggregate-internal rejection event with no such signal stays `itIgnores*`.
- Query Handler: success `itGets*` / `itLists*` / `itLists*By*` / `itPaginates*`, failure `itFailsWhen*`. A Query returning `PaginatedResult<X>` gets exactly one success test, `itPaginates` — never a separate `itLists`/`itPaginates` pair. `// Given` seeds the fixture and captures expected ids; `// When` calls `Shared\Tests\Support\PaginationTrait::traversePages()`, which fetches every page plus one out-of-bounds page and asserts item order/pagination metadata on each, returning the in-bounds pages; `// Then` reads those pages for whatever hydration/domain assertions the DTO shape calls for. `itPaginatesWhenEmpty` calls the trait's `traverseEmptyPage()` instead — pure mechanic. A filtered/sorted Query's own `itLists*By*`/`itSortsBy*` stays decoupled from the trait — one page, id/order-only, no pagination/DTO re-check.
- A Command/Query Handler's own `itFailsWhenNotFound` never names the lookup field (`WhenIdNotFound`), bare `WhenNotFound` always — it resolves exactly one aggregate through exactly one id.
- Side effect (`#[Policy]` or `#[Processor]`, same test shape for both): `it<Verb>`, bare — same shape as a Publisher's own test, no dedicated failure shape. A guard branching on the triggering item's absence gets its own negative control, `itIgnoresWhen*`, same idiom as a Command Handler's no-op, never `itDoesNothingWhen*` — `itDoesNot*` stays reserved for the isolated Domain Aggregate test. No such guard, no negative control. A noun the class name already fixes is never repeated inside the method name.
- Publisher: `itPublishes`, bare — one test method per class, no dedicated failure shape.
- Validation compound (`CompoundConstraintTestCase`): success `itAccepts`, failure `itRefuses` (one data set per refused value, per the Structure convention above).
- A `#[DrivingPort]` method returning a plain `bool` with no exception on refusal follows the same accept/refuse shape: `itAccepts`/`itRefuses`, one test method per outcome — `itRejects*`/`itFailsWhen*` never substitute for it.
- A `<X>Status`'s own boolean predicate, exercised by iterating every case in one test: `it{Predicate}` (mirrors the method name, e.g. `itIsActive` for `isActive()`) — never a trailing `OnlyWhen<CurrentCase>` naming today's exact case set as if it were the contract.
