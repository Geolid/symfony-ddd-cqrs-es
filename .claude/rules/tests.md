## Rules

**ALWAYS**
- Test methods carry the `#[Test]` attribute.
- Code is organized in three blocks separated by blank lines: `// Given`, `// When`, `// Then`. A block covering more than one distinct concern may insert its own blank line between each concern's statements without breaking the outer three-block separation. For an exception test where the call under test itself throws, `// Then` (`expectException()`) comes before `// When`. When the call under test succeeds and a later verification read is what actually throws (e.g. a Finder lookup confirming a deleted read-side row is gone), the real action stays alone in `// When`, and `expectException()` moves into `// Then` immediately before that verifying call instead. The call under test is always assigned to a variable inside `// When` — `// Then` only asserts against already-computed values, never invokes anything inline inside an assertion, except a pure, side-effect-free read already resolved off an object already in scope. A test whose sole subject is a void call delegated to a mocked collaborator has no `// Then` — the collaborator's own `expects()`, configured in `// Given`, is the whole verification, and nothing computed exists afterward to assert.
- A Finder call repeated in the same test against the same entity, outside an explicit before/after comparison, reduces to a single call reused wherever its result is needed — never literally one call per distinct thing checked (the subject, a decoy, each item of a batch each still gets its own single call).
- A Repository call repeated in the same test against the same entity, outside an explicit before/after comparison, reduces to a single call reused wherever its result is needed — same reasoning as the Finder rule above, never literally one call per distinct thing checked. A test whose own name already names more than one Repository method as its subject (a round-trip test asserting both presence and content) is exempt for each method its name covers — that repetition is the named contract, not redundancy.
- A `// Given` block ends in exactly one `$this->store(...)` call, combining every aggregate it built. A second aggregate's construction referencing a first one's id never needs that first aggregate persisted first — the id is already known (generated before persistence), so nothing blocks building both and storing them together. A state-transition needed on a built aggregate before the test's own subject runs is expressed as a factory transition building the aggregate in its final state up front, never as a direct call on the aggregate between two separate `store()` calls. A second `store()` after `// Given` is only ever legitimate inside `// When`, when persisting again is itself the behavior under test (e.g. a Projector reacting to the newly persisted event). One `store()` call still orders its arguments deliberately when a built-in-final-state aggregate's own transition cascades an Integration Event whose Projector reaction writes into another passed aggregate's own row by reference (an `UPDATE` keyed by id, not the row's own creating `INSERT`) — that referenced aggregate goes first in the argument list, since the cascade only lands once its row already exists. A blank line right before that final `store()` call is used only when it concludes a concern distinct from the statements directly above it — never inserted just because `store()` sits last. A pure baseline read with no construction or mutation of its own, needed only for a later before/after comparison and depending on the just-stored aggregate's own projection, may follow that call — the rule targets aggregate-construction discipline, not every read.
- A `// Given` combining a subject under test with a generic decoy ("other"/"others") declares the decoy first, the subject last — combined into one `store()` call, same order, spread argument last (PHP forbids a positional argument after one). A subject created after its decoy always sorts after it in a collection's own default order, so a mutant that drops a filter/lookup can't coincidentally return the subject instead of the decoy.
- Every factory build is assigned to its own bare, descriptive local variable first, never an inline `X::new()->...->create()` passed straight into `store()` — including a lone, single-item `store()` call. A factory chain spanning several lines puts `X::new()` alone on the first line, one call per line, and `create()` alone on the last.
- A value a test doesn't care about the exact content of is left to the factory default, a Value Object's own factory, or `faker()` — never hand-typed. A literal or explicit `with*()` override is reserved for a value whose exact content is itself the scenario under test (a wrong password, a malformed code) — never for data merely needed to produce a valid fixture. A value read back for an assertion is read off the aggregate's own properties; a secret the aggregate keeps only derived (a hash, a ciphertext) is drawn first (`faker()->apiKeySecret()`), passed through `with*()` and reused. Two or more aggregates of the same type in a test are named after their own role, never all generically the same name.
- A foreign aggregate's own id/reference field carried on the aggregate under test (an owning entity's id, referenced by string per `domain.md`) is left to the subject's OWN factory default for that field, never read from the foreign aggregate's factory, unless the foreign aggregate is itself genuinely built and stored in that same test (its real state is read back, or the test's own subject depends on it existing). An id of the aggregate's own BC is built through its Value Object factory (`<X>IdFactory`), a foreign one through `Uuid::uuid7()->toString()`.
- An identical construction (a `service(<X>::class)` resolution, a Stub/Gateway build, a value transformation/mapping with a repeated shape) repeated across two or more call sites in the same test class is hoisted once instead of repeated — a property resolved in `setUp()` when the call sites are instance methods, a `private static` helper when they're static (a data provider). Exception: a Web test case, where `setUp()` runs before the test method's own `self::browser()`/`createClient()` call — resolving a service that early boots the kernel out of order (`LogicException: Booting the kernel before calling createClient()...`), so the repeated resolution stays inline there. A bare factory call is never wrapped this way regardless of repetition count — the factory itself is already the extracted abstraction, and `// Given` shows its own setup inline (locality of behavior over deduplication) rather than through a further indirection that also blocks fluent chaining at the call site.
- A repeated bare literal is never extracted into its own local variable purely because it appears at two or more call sites — extraction there is earned only once the literal itself is long or descriptive enough to become a real duplication risk. A computed or derived expression (an arithmetic offset, a concatenation, any value assembled at the call site rather than hand-typed as-is) is extracted regardless of its own length the moment it repeats across two or more call sites instead: its value must stay identical between them, and re-evaluating the same expression by eye at each site to confirm that carries a real risk a short literal never does.
- The same reasoning holds across files, not only within one: a local test fixture (a literal dataset, a small array) duplicated verbatim across two or more test files stays duplicated rather than hoisted into a shared location. DAMP — each file staying fully self-contained and explicit on its own — outranks DRY for this kind of test-local data; hoisting is reserved for what a factory or a shared double already centralizes on its own merits, never invented just because two files happen to need the same literal shape.
- Success and failure cases for the same behavior are grouped together, success first. A no-op success (`itIgnores*`) groups with the success side, before every `itFailsWhen*` — it never throws, so it stays on the non-throwing side of the split regardless of where its own guard sits in the real execution sequence.
- Multiple failure cases for the same behavior are ordered to mirror the sequence their guards actually run in the code under test — never insertion order, never alphabetical by exception name.
- A relational-operator comparison against a threshold (`<`/`<=`/`>`/`>=`, e.g. a window/retention policy's expiry check) is tested exactly at the boundary value, not only clearly-before/clearly-after — otherwise a mutant flipping the operator's inclusivity survives unnoticed. An exact-boundary case in a compound with more than one rule on the same value must satisfy every other rule too — verify first, drop the case if two rules conflict at that edge.
- Two or more related timestamps anywhere in the same test (a plain `TestCase`/`#[DataProvider]` included, not only the `AggregateRootTestCase`/`AbstractIntegrationTestCase` shapes below) are expressed as one local anchor plus `modify()` off it, never as separate hand-typed `\DateTimeImmutable` literals.

**NEVER**
- Mock an Aggregate or a Result object directly — build it through the matching factory instead of a test double.
- Call `expects()` on a `createStub()` — a stub simulates a return value, a mock (`createMock()` + `expects()`) verifies a behavior.
- Suffix a variable with `Mock`/`Stub` — use the short class name (`$repository`) or the constructor argument's name when several dependencies share a type.
- Use a literal value that doesn't match the real field's format — a UUID-typed id gets a fake UUID (e.g. `Uuid::uuid7()->toString()`), not an arbitrary string.
- Hardcode another BC's vocabulary as a literal — use a generic/fake value instead.
- Wrap a Value Object's own `equals()` call in `assertTrue`/`assertFalse` as a shortcut for comparing structured data, when the test's actual subject is that data surviving a round-trip or crossing a boundary correctly (not the VO's own `equals()` implementation) — on failure it only reports `false` was not `true`, with no indication of which field diverged. Compare a primitive array of every field on both sides through `assertSame` instead, so a mismatch shows which one. `assertTrue($vo->equals($other))` stays correct where the VO's own `equals()` behavior genuinely is the test's subject (a dedicated equality test for that VO).
- Assert a closed vocabulary through the enum foreign to the layer under test — a Domain aggregate test (`given()`/`when()`/`then()`, a transition's guard) compares against `<X>State`; an Application/Infrastructure/DM test (a Finder `Result`, a Projector row, a webhook/API response) compares against `<X>Status` — the two never substitute for each other even where their case values currently coincide.

## Conventions

### Naming
- Method names: `it{Verb}*` — bare, no implementation detail. The verb is always active, mirroring the method it exercises (`itDelivers`, `itCancels`) — never passive (`itIsDelivered`).
- The test class already fixes the subject under test — a method name never repeats it as a noun. The same holds for a condition: a class already named after the one scenario its single test exercises doesn't restate that scenario in the method name either — it reduces to the bare verb.
- "On" names a reaction to an already-recorded fact (a Policy/Processor/Projector's own shape) — never reused elsewhere for an unrelated meaning (e.g. a gateway's own failure condition), since out of that context it misreads as the same reactive shape.
- An article ("a", "an", "the") is dropped wherever it precedes a noun. It stays only where dropping it would leave an adjective or relative clause with no noun left to attach to — reword instead of leaving it dangling.
- A quantifier ("Every", "Both", "All"...) never restates a completeness guarantee the architecture already provides — a batch operation that always acts on its full filtered collection by construction needs no quantifier, the plural noun alone already conveys the whole matching set. It stays legitimate to name an actual multi-condition business fact (a genuine AND/OR the system could satisfy incorrectly) that isn't already carried by a data provider's own case labels.
- A state/trigger condition always connects with "When" — never a synonym ("Once", "Yet", "After"...), whether the condition is a state, an elapsed duration, or an actor's action. The linking verb ("is", "was") inside that condition is dropped the same way as an article, once the subject noun it refers to is already gone — `WhenNotFound`, never `WhenIsNotFound` or `WhenOrderIsNotFound`.
- A negated need/requirement condition is phrased as the subject noun followed by postposed "Not" (`WhenRehashNotNeeded`), the same shape as `WhenNotFound` — never a preposed quantifier ("WhenNoRehashNeeded").
- "When" and "With"/"Without" never substitute for each other: "When" names a precondition already true of the system before the call (a state, an elapsed duration, a related record's own shape); "With"/"Without" names an argument or payload value the caller supplies on the call itself. A fact only ever readable off the system's own prior state, never off the call's input, stays "When" even if it superficially reads like a qualifier on the actor's action.
- A test's name covers exactly what it asserts, nothing more — an assertion outside that scope belongs in a separate test. The reverse also holds: one success case covers its full contract in a single test — never fragment it across near-duplicate tests replaying the same call.
- An `assertSame` comparing two `->format(...)` calls on both sides (a date compared against another date, both formatted the same way) is broken onto its own multi-line call, one argument per line — a single-side `->format(...)` compared against a plain scalar (a row's own already-string field, an id) stays inline, it's already short enough to read on one line.
- `// Then`'s direct reads off a Result/row (`$result->x`, `$row['x']`) come first, in the Result's own field order — a computed field among them (e.g. two `->format()` calls compared to each other) stays in that same natural order, no blank line, when it's just another one of the Result's own fields for the same subject. An assertion that isn't itself one of the Result's own listed fields (a hasher's `hash()`/`verify()` against a stored hash, a secret compared against it) goes last instead, separated by its own blank line, so it never interrupts the straight top-to-bottom reading of the Result's own fields.
- Two independent cases exercising the same call with no shared narrative (a strength check against two unrelated literal passwords, a gateway against two unrelated collaborator configurations, a Value Object's own `equals()` against a same-value/different-value pair) never share one test body — a `#[DataProvider]` when only the literal input varies with identical setup, two separate test methods when the setup/collaborator itself differs per case, or when a Value Object's own `equals()` is the subject (`itEquals`/`itDiffers`, split even though a provider is technically possible — a Value Object equality test reads more clearly as two named outcomes than as data-set labels). This stays distinct from a single coherent contract that genuinely needs more than one assertion to verify in full (a decoy's isolation check against the one subject under test) — that one stays a single test, per the "covers its full contract" rule above.
- A Repository's `has()` existence check splits into two tests, one per outcome — `itHas` (found), `itHasNot` (not found) — never combined into one test asserting both a present and an absent id. `itHasNot` stays distinct from `itDoesNot*`, reserved for an Aggregate's own re-entry no-op.
- Failure naming: the qualifier reflects the exception the test expects — its own name already carries whether the failure is a business rule or a technical constraint. When the same exception can be thrown from more than one distinct trigger, the qualifier instead names that specific trigger/condition, so sibling tests stay distinguishable — never the bare exception name repeated identically across them.
- Data providers: `provide[Context]`, `#[DataProvider]` attribute, `yield` with a descriptive label.
- A private static helper building a default valid value with overridable keys (consumed by name from a data provider) is named after the bare concept it builds, never prefixed by a qualifier word — the qualifier adds no information the helper's own return type and call sites don't already carry.
- A hand-written test double is prefixed by its real role, never a blanket term: `Dummy` when it has zero behavior beyond satisfying a type, `Stub` when it returns a canned/configurable answer with no real logic, `Fake` when it's a genuinely working simplified implementation, `Spy` when the point is an interaction recorded for a later assertion. The same role naming carries into a trait wrapping `createStub()`/`createMock()` instead of a hand-rolled class (`<Interface>StubTrait`) — the right shape once only one method of a multi-method interface is ever exercised across every call site, so the vendor-generated stub covers every other method with no dead hand-written override. A class/enum/trait used by a single test is declared at the bottom of that test file; one reused across two or more test files moves to a `Support/Double/` folder instead (scoped to the narrowest BC/subdomain all its callers share) — reserved for an artifact whose own job is producing/representing a double. A helper that only wires vendor/framework ceremony around an object it's handed (real or double, indifferently) isn't itself a double and stays at `Support/`'s own root instead, never inside `Double/`.
- A double for a vendor class is written only after checking that class's own constructor/API for a built-in substitution flag (a disable switch, an injectable client) — never hand-roll one already available. A Stub/Fake's canned output stays recognizably fake even under a technical constraint (fixed length, charset) — truncate/pad the existing pattern first, a real algorithm only once that can't satisfy it.
- The DAMP-over-DRY call for test-local fixture data above never extends to a double's own mechanics. Inline `createMock()`/`createStub()` configuration for the same port, hand-repeated with the same canned answers across 2+ test files, is a genuine DRY case — a port's own interface change (a renamed method, an added argument) then means fixing every one of those call sites instead of one. Centralize into a real named `Stub`/`Fake` in `Support/Double/` once that repetition is real, same threshold as the class-reuse rule above — a hand-rolled class implementing the port when every one of its methods is realistically coverable, a `StubTrait` wrapping `createStub()`/`createMock()` instead when only one method of a multi-method port is ever exercised (per the naming convention above). What still stays DAMP regardless of that centralization is the data/intent a test hands to the double at its own call site — an explicit configuration call in `// Given`, never hidden behind a further layer of indirection. A `Dummy` carries no configuration either way, so this tension never applies to it.

### Factory
- `<Aggregate>Factory extends Support\Foundry\AbstractAggregateFactory`, one per aggregate, colocated at `tests/<Subdomain>/<Bc>/Support/Factory/`. A Value Object has its own `<Vo>Factory` (an `ObjectFactory` calling the VO's named constructor through `Instantiator::namedConstructor()`), colocated the same way — `tests/Shared/Support/Factory/` for a Shared one. A faker provider never returns a Value Object, only a primitive (`CredentialFakerProvider`, `CountryCodeFakerProvider`); each provider class is declared under `faker.providerClasses` in `tests/phpstan.neon` and `apps/phpstan.neon`.
- `defaults()` returns each attribute as its downstream type: a nested Value Object factory, a faker-backed primitive, a date derived from one `$now = Clock::get()->now()` anchor through `modify()`. `build()` calls the aggregate's own named factory with named arguments from the resolved parameters. An attribute derived from another (an id from a parent id, items from a currency) is resolved in `beforeInstantiate` with `??=` from the final value, so a `with*()` override carries over.
- `with<Key>()` exists for each attribute `build()` consumes, converting a primitive to its stored type and merging through `with()`; an id derived from another key, and a key consumed only by a transition's own optional parameter, get none.
- Every state-transition the aggregate exposes gets a matching `transition()`, same order as the aggregate's own methods, wrapping exactly one transition — never another transition to reach its starting state — so transitions chain in the aggregate's real lifecycle order. A transition's optional parameter exists only for a value with no other override path; its default is an attribute in `defaults()`.
- `create()` returns one aggregate; `many(n)->create()` returns `list<Aggregate>`. A factory never persists — persisting is `$this->store(...)` on the built aggregate(s).
- A test reads a built aggregate through its own `public private(set)` properties; the root id is read off the aggregate (`$x->id->toString()`), or from the id's Value Object factory when no aggregate exists.
- Two branches in the same test that would otherwise repeat an identical transition prefix of 3 or more calls before diverging on one trailing call share that prefix as a single instance instead, reassigned under the subject's own variable name as it advances — a factory's immutability keeps the earlier reference untouched. Never collapse the prefix when either branch's own argument differs at the shared depth, nor when the second branch is a decoy deliberately left at its own baseline.

### Story
- A Story (`Support\Foundry\Story\AbstractAggregateStory`) is a named scenario spanning aggregates or BCs — one class per scenario, colocated at `tests/<Subdomain>/Support/Story/` (`apps/<dm>/tests/Support/Story/` until a second DM needs it), named after what it sets up, never after a test. It persists through `persist()` (the Repository) and exposes what a test reads as named states (`addState()`), read back through a static accessor; a secret the aggregates keep only derived is drawn from the faker first and exposed as state.
- A Story is applied with `#[WithStory(<Story>::class)]` on the test method (a `KernelTestCase`) and rebuilt for every test; it takes no call-time parameter — a variation is another Story. Stories stack by reading a lower one's state.
- A Given covering a single aggregate stays inline with factories; a Story earns its place once a named scenario is shared by several tests or spans aggregates. A Story encoding more than its name states is a Mystery Guest.

### Test doubles
- An integration test's double strategy follows its own subject, never a collaborator's cost or determinism. A storage-boundary test (Repository/Finder/Projector) has its own round-trip to storage as sole subject: a service collaborator needed merely to build a valid Aggregate through its factory is doubled, deterministically — its own correctness belongs to that service's own dedicated test. A Value Object carried across that same boundary is never doubled this way, it's the data under test, not a service. A use-case test (a Command/Query Handler, or an Application port exercised directly by a Delivery Mechanism) has the whole orchestration as its subject instead: every in-process collaborator is wired for real; only a boundary actually leaving the process (a vendor call, a transport) gets doubled there.

### Event Sourcing (`Patchlevel\EventSourcing\PhpUnit\Test\AggregateRootTestCase`)
- `given(...events)->when(fn (Aggregate $a) => ...)->then(...expectedEvents)` — the standard shape for an aggregate unit test.
- `expectsException(...)` replaces `then(...)` for a failure case.
- `setUp()` hoists every field the aggregate's own creation factory needs, plus every field a `given()`-reused intermediate event needs, as typed properties sourced from Value Object factories, faker primitives and one `$now = Clock::get()->now()` anchor with `modify()` — never a hand-typed literal, never a second `Clock::get()->now()`/`new \DateTimeImmutable(...)` call. The root id comes from its own `<X>IdFactory`. A value needed by only one test method (an argument to a single transition, a redundant re-entry timestamp with no other reuse) is drawn inline inside that test instead of hoisted to a property.
- Each event reused as a `given()` baseline across 2+ test methods gets its own `private function <event>(): <Event>` instance helper, reading the hoisted properties — named after the fact it records, mirroring the aggregate's own transition method it results from. An event built and consumed within a single test (a terminal/one-off transition with no later test building on top of it) stays inline, constructed directly at its one call site — no helper for it.
- A closure passed to `when()` is `static` whenever it reads no hoisted property (every value it needs is a local variable already in scope) — plain `fn` the moment it reads even one `$this->` property.
- A static `#[DataProvider]` cannot reach instance properties — it draws its own fixture values the same way (factories, faker, a `Clock::get()->now()` anchor), building any reused raw payload (a foreign Value Object's own primitive shape carried on an event) through a shared `private static` helper so the instance side and the provider side never duplicate that mapping.

### CQRS / container (`Support\TestCase\AbstractIntegrationTestCase`)
- `dispatch()` sends a Command to the Command bus; `ask()` runs a Query and returns its result.
- `service()` resolves a service from the container with a type assertion on the given class/interface. `serviceAs()` resolves a service whose container ID differs from the PHP type it's expected to be (e.g. a Doctrine alias).
- A Policy or Processor is exercised directly — construct/fetch it and invoke it with the event it subscribes to — rather than relying on a running subscription worker in the test suite. This is specific to `AbstractIntegrationTestCase`'s own `patchlevel_event_sourcing` config (`store()` only triggers the `publisher`/`projector` groups there); an E2E/web test case may deliberately enable the `Policy`/`Processor` groups too, for realistic side effects (an actual email sent, a real cascading reaction) — never assume the two share the same config.
- `store()` persists and triggers the `publisher` then `projector` groups (never the `#[Policy]`/`#[Processor]` side effects).
- `publishedEventOf(string $eventClass)` returns the persisted event of that type, scanning the whole store.
- Every check against "now" — a passive TTL/expiry read included, whether or not any `#[Policy]`/cron reacts to time passing — reads `Clock::get()->now()` as its anchor, never a hand-typed static date: the suite-wide `ClockExtension` already freezes `Symfony\Component\Clock\Clock`'s global singleton to one fixed instant before any test runs, and the container's own `clock` service has no inner clock of its own, so it already proxies that same frozen singleton. A test never overrides the container's `clock` service with its own `MockClock` instance — that creates a second, independent clock diverging from `Clock::get()->now()`, which every factory default already reads from.
- Every fixture timestamp in a test is expressed as `$now->modify('-2 hours')`/`modify('-3 days')` off that one frozen `Clock::get()->now()` anchor — never a second, independently hand-typed `\DateTimeImmutable` literal per fixture. The delta itself must read as a plausible real-world gap for what it represents (an order refunded hours or days after capture, never open-endedly far apart) — a `stuck`/`fresh` pair straddles the threshold by a small, deliberate margin on each side, not an arbitrary date picked for arithmetic convenience.
- A Command Handler test's own `// Then` reads the outcome through the Finder/Read Model, never through the write-side Repository — a Repository load in a use-case test is reserved for a Repository's own dedicated test. A field the projection doesn't carry is a projection gap to fix (add the column/subscriber), never a reason to load the aggregate directly as a substitute.
- A creation Handler's own idempotency on a second dispatch of the same id (a `catch (<Agg>AlreadyExistsException)` around `save()`, kept even with no `has(id)` pre-check in front of it — that pre-check is never added at all, since it can't close the race either way) is exercised by dispatching the same Command twice: the test environment's event store is the real database one, so the second `save()` raises the store's own already-exists rejection. The Repository's own dedicated test covers the exception itself — one aggregate stored through `store()`, a second with the same id passed to `save()` in `// When`.
