## Rules

**ALWAYS**
- Test methods carry the `#[Test]` attribute.
- Code is organized in three blocks separated by blank lines: `// Given`, `// When`, `// Then`. A block covering more than one distinct concern may insert its own blank line between each concern's statements without breaking the outer three-block separation. For an exception test where the call under test itself throws, `// Then` (`expectException()`) comes before `// When`. When the call under test succeeds and a later verification read is what actually throws (e.g. a Finder lookup confirming a deleted read-side row is gone), the real action stays alone in `// When`, and `expectException()` moves into `// Then` immediately before that verifying call instead. The call under test is always assigned to a variable inside `// When` — `// Then` only asserts against already-computed values, never invokes anything inline inside an assertion, except a pure, side-effect-free read already resolved off an object already in scope.
- A Finder call repeated in the same test against the same entity, outside an explicit before/after comparison, reduces to a single call reused wherever its result is needed — never literally one call per distinct thing checked (the subject, a decoy, each item of a batch each still gets its own single call).
- A Repository call repeated in the same test against the same entity, outside an explicit before/after comparison, reduces to a single call reused wherever its result is needed — same reasoning as the Finder rule above, never literally one call per distinct thing checked. A test whose own name already names more than one Repository method as its subject (a round-trip test asserting both presence and content) is exempt for each method its name covers — that repetition is the named contract, not redundancy.
- A `// Given` block ends in exactly one `$this->store(...)` call, combining every aggregate it built. A second aggregate's construction referencing a first one's id never needs that first aggregate persisted first — the id is already known (generated before persistence), so nothing blocks building both and storing them together. A state-transition needed on a built aggregate before the test's own subject runs is expressed as a Builder modifier building the aggregate in its final state up front, never as a direct call on the aggregate between two separate `store()` calls. A second `store()` after `// Given` is only ever legitimate inside `// When`, when persisting again is itself the behavior under test (e.g. a Projector reacting to the newly persisted event). One `store()` call still orders its arguments deliberately when a built-in-final-state aggregate's own transition cascades an Integration Event whose Projector reaction writes into another passed aggregate's own row by reference (an `UPDATE` keyed by id, not the row's own creating `INSERT`) — that referenced aggregate goes first in the argument list, since the cascade only lands once its row already exists. A blank line right before that final `store()` call is used only when it concludes a concern distinct from the statements directly above it — never inserted just because `store()` sits last.
- A `// Given` combining a subject under test with a generic decoy ("other"/"others") declares the decoy first, the subject last — combined into one `store()` call, same order, spread argument last (PHP forbids a positional argument after one). A subject created after its decoy always sorts after it in a collection's own default order, so a mutant that drops a filter/lookup can't coincidentally return the subject instead of the decoy.
- Every Builder build is assigned to its own bare, descriptive local variable first, never an inline `X::new()->...->create()` passed straight into `store()` or a modifier chain — including a lone, single-item `store()` call.
- A value a test doesn't care about the exact content of is sourced from its Builder (`$builder['key']`, or an unread `defaults()` value) rather than hand-typed. A literal or explicit `with*()` override is reserved for a value whose exact content is itself the scenario under test — never for data merely needed to produce a valid fixture. One Builder instance is built per conceptual entity and read from repeatedly for its own attributes — never re-instantiated for another read of the same entity; two or more such instances in the same test are named after their own role, never all generically the same name.
- A foreign aggregate's own id/reference field carried on the aggregate under test (an owning entity's id, referenced by string per `domain.md`) is sourced from the subject's OWN Builder default for that field, never from the foreign aggregate's Builder, unless the foreign aggregate is itself genuinely built and stored in that same test (its real state is read back, or the test's own subject depends on it existing). A Builder that already carries an independent generator for that reference field makes reaching into the foreign one redundant regardless of whether the two happen to produce the same-shaped value.
- An identical construction (a `service(<X>::class)` resolution, a Stub/Gateway build, a value transformation/mapping with a repeated shape) repeated across two or more call sites in the same test class is hoisted once instead of repeated — a property resolved in `setUp()` when the call sites are instance methods, a `private static` helper when they're static (a data provider). Exception: a Web test case, where `setUp()` runs before the test method's own `self::browser()`/`createClient()` call — resolving a service that early boots the kernel out of order (`LogicException: Booting the kernel before calling createClient()...`), so the repeated resolution stays inline there. A bare Builder call is never wrapped this way regardless of repetition count — the Builder itself is already the extracted abstraction, and `// Given` shows its own setup inline (locality of behavior over deduplication) rather than through a further indirection that also blocks fluent chaining at the call site.
- Success and failure cases for the same behavior are grouped together, success first. A no-op success (`itIgnores*`) groups with the success side, before every `itFailsWhen*` — it never throws, so it stays on the non-throwing side of the split regardless of where its own guard sits in the real execution sequence.
- Multiple failure cases for the same behavior are ordered to mirror the sequence their guards actually run in the code under test — never insertion order, never alphabetical by exception name.
- A relational-operator comparison against a threshold (`<`/`<=`/`>`/`>=`, e.g. a window/retention policy's expiry check) is tested exactly at the boundary value, not only clearly-before/clearly-after — otherwise a mutant flipping the operator's inclusivity survives unnoticed. An exact-boundary case in a compound with more than one rule on the same value must satisfy every other rule too — verify first, drop the case if two rules conflict at that edge.
- Two or more related timestamps anywhere in the same test (a plain `TestCase`/`#[DataProvider]` included, not only the `AggregateRootTestCase`/`AbstractIntegrationTestCase` shapes below) are expressed as one local anchor plus `modify()` off it, never as separate hand-typed `\DateTimeImmutable` literals.

**NEVER**
- Mock an Aggregate or a Result object directly — build it through the matching Builder instead of a test double.
- Call `expects()` on a `createStub()` — a stub simulates a return value, a mock (`createMock()` + `expects()`) verifies a behavior.
- Suffix a variable with `Mock`/`Stub` — use the short class name (`$repository`) or the constructor argument's name when several dependencies share a type.
- Use a literal value that doesn't match the real field's format — a UUID-typed id gets a fake UUID (e.g. `Uuid::uuid7()->toString()`), not an arbitrary string.
- Hardcode another BC's vocabulary as a literal — use a generic/fake value instead.
- Wrap a Value Object's own `equals()` call in `assertTrue`/`assertFalse` as a shortcut for comparing structured data, when the test's actual subject is that data surviving a round-trip or crossing a boundary correctly (not the VO's own `equals()` implementation) — on failure it only reports `false` was not `true`, with no indication of which field diverged. Compare a primitive array of every field on both sides through `assertSame` instead, so a mismatch shows which one. `assertTrue($vo->equals($other))` stays correct where the VO's own `equals()` behavior genuinely is the test's subject (a dedicated equality test for that VO).
- Assert a closed vocabulary through the enum foreign to the layer under test — a Domain aggregate test (`given()`/`when()`/`then()`, a transition's guard) compares against `<X>State`; an Application/Infrastructure/DM test (a Finder `Result`, a Projector row, a webhook/API response) compares against `<X>Status` — the two never substitute for each other even where their case values currently coincide.

## Conventions

### Naming
- Method names: `it{Verb}*` — bare, no implementation detail. The verb is always active, mirroring the method it exercises (`itDelivers`, `itCancels`) — never passive (`itIsDelivered`).
- The test class already fixes the subject under test — a method name never repeats it as a noun. The same holds for a condition: a class already named after the one scenario its single test exercises doesn't restate that scenario in the method name either — it reduces to the bare verb.
- "On" names a reaction to an already-recorded fact (a Policy/Projector's own shape) — never reused elsewhere for an unrelated meaning (e.g. a gateway's own failure condition), since out of that context it misreads as the same reactive shape.
- An article ("a", "an", "the") is dropped wherever it precedes a noun. It stays only where dropping it would leave an adjective or relative clause with no noun left to attach to — reword instead of leaving it dangling.
- A quantifier ("Every", "Both", "All"...) never restates a completeness guarantee the architecture already provides — a batch operation that always acts on its full filtered collection by construction needs no quantifier, the plural noun alone already conveys the whole matching set. It stays legitimate to name an actual multi-condition business fact (a genuine AND/OR the system could satisfy incorrectly) that isn't already carried by a data provider's own case labels.
- A state/trigger condition always connects with "When" — never a synonym ("Once", "Yet", "After"...), whether the condition is a state, an elapsed duration, or an actor's action. The linking verb ("is", "was") inside that condition is dropped the same way as an article, once the subject noun it refers to is already gone — `WhenNotFound`, never `WhenIsNotFound` or `WhenOrderIsNotFound`.
- A negated need/requirement condition is phrased as the subject noun followed by postposed "Not" (`WhenRehashNotNeeded`), the same shape as `WhenNotFound` — never a preposed quantifier ("WhenNoRehashNeeded").
- "When" and "With"/"Without" never substitute for each other: "When" names a precondition already true of the system before the call (a state, an elapsed duration, a related record's own shape); "With"/"Without" names an argument or payload value the caller supplies on the call itself. A fact only ever readable off the system's own prior state, never off the call's input, stays "When" even if it superficially reads like a qualifier on the actor's action.
- A test's name covers exactly what it asserts, nothing more — an assertion outside that scope belongs in a separate test. The reverse also holds: one success case covers its full contract in a single test — never fragment it across near-duplicate tests replaying the same call.
- An `assertSame` comparing two `->format(...)` calls on both sides (a date compared against another date, both formatted the same way) is broken onto its own multi-line call, one argument per line — a single-side `->format(...)` compared against a plain scalar (a row's own already-string field, an id) stays inline, it's already short enough to read on one line.
- `// Then`'s direct reads off a Result/row (`$result->x`, `$row['x']`) come first, in the Result's own field order — an assertion needing extra computation on top of a plain read (a hasher's `hash()`/`verify()` against a stored hash, a secret compared against it) goes last, separated by its own blank line, so it never interrupts the straight top-to-bottom reading of the Result's own fields.
- Two independent cases exercising the same call with no shared narrative (a strength check against two unrelated literal passwords, a gateway against two unrelated collaborator configurations, a Value Object's own `equals()` against a same-value/different-value pair) never share one test body — a `#[DataProvider]` when only the literal input varies with identical setup, two separate test methods when the setup/collaborator itself differs per case, or when a Value Object's own `equals()` is the subject (`itEquals`/`itDiffers`, split even though a provider is technically possible — a Value Object equality test reads more clearly as two named outcomes than as data-set labels). This stays distinct from a single coherent contract that genuinely needs more than one assertion to verify in full (a decoy's isolation check against the one subject under test) — that one stays a single test, per the "covers its full contract" rule above.
- A Repository's `has()` existence check splits into two tests, one per outcome — `itHas` (found), `itHasNot` (not found) — never combined into one test asserting both a present and an absent id. `itHasNot` stays distinct from `itDoesNot*`, reserved for an Aggregate's own re-entry no-op.
- Failure naming: the qualifier reflects the exception the test expects — its own name already carries whether the failure is a business rule or a technical constraint. When the same exception can be thrown from more than one distinct trigger, the qualifier instead names that specific trigger/condition, so sibling tests stay distinguishable — never the bare exception name repeated identically across them.
- Data providers: `provide[Context]`, `#[DataProvider]` attribute, `yield` with a descriptive label.
- A private static helper building a default valid value with overridable keys (consumed by name from a data provider) is named after the bare concept it builds, never prefixed by a qualifier word — the qualifier adds no information the helper's own return type and call sites don't already carry.
- A hand-written test double is prefixed by its real role, never a blanket term: `Dummy` when it has zero behavior beyond satisfying a type, `Stub` when it returns a canned/configurable answer with no real logic, `Fake` when it's a genuinely working simplified implementation, `Spy` when the point is an interaction recorded for a later assertion. A class/enum used by a single test is declared at the bottom of that test file; one reused across two or more test files moves to a `Support/Doubles/` folder instead (scoped to the narrowest BC/subdomain all its callers share).
- A double for a vendor class is written only after checking that class's own constructor/API for a built-in substitution flag (a disable switch, an injectable client) — never hand-roll one already available. A Stub/Fake's canned output stays recognizably fake even under a technical constraint (fixed length, charset) — truncate/pad the existing pattern first, a real algorithm only once that can't satisfy it.

### Builder
- `<Aggregate>Builder extends Support\Builder\AbstractAggregateBuilder`, one per aggregate, colocated at `tests/<Subdomain>/<Bc>/Support/Builder/` — the abstract base class itself lives at the repo-wide `tests/Support/Builder/`, never under a specific BC or under `Shared`, since it mirrors nothing in `src/` and every BC's own Builder depends on it. Its call-site local variable is named `$builder`/`$<x>Builder`, matching the class — the class itself combines the Test Data Builder pattern (fluent `with*()`/modifier chaining) with an Object Mother (named `sample()`/`defaults()` scenarios), but the fluent-chaining half is the one actually exercised at every call site.
- `defaults()` returns attributes already typed as the Value Object each carries downstream (never the primitive an outside caller supplies) — Faker-backed (`Support\SeededFaker::get()`, called directly — no factory-level wrapper). The aggregate's own creation-timestamp attribute is a lazy closure reading `Clock::get()->now()`, same shape as every other date attribute — never `Support\ClockSequence::next()` called directly inside `defaults()`, since `create()` already seeds a frozen clock from that same sequence once per call. `build()` takes no parameter — it reads each field through `$this['key']` and calls the aggregate's own named factory with named arguments — never a bare constructor, never a repeated `Assert::` block reconstructing what the generic accessor's own per-key return type already guarantees.
- `with*()` methods keep their own parameter primitive for calling-test ergonomics, converting to the stored Value Object internally before merging — `withId(string $id)` stores `SomeId::fromString($id)`, never the raw string. They return a new instance via `$this->withAttributes(key: $value)` — `withAttributes()` takes its overrides as named, variadic arguments (`mixed ...$attributes`), never a single array-literal parameter — a partial override, never `array_merge($this->attributes, [...])` first (`withAttributes()` on the base class already merges onto the current attributes) and never `static::new(...)` directly: `$attributes` is `readonly`, so a fresh instance is unavoidable, but `withAttributes()` also carries the already-chained modifiers over to it; `static::new()` alone would silently drop them if a `with*()` is chained after a modifier. A state-transition modifier (e.g. `cancelled()`) uses `withModifier()` and calls the real aggregate method. It wraps exactly one transition — never another modifier internally to reach its own starting state — so modifiers stay chainable in the same order as the aggregate's real lifecycle (`dispatched()->tracked('X')->delivered()`, not a `delivered()` that redundantly dispatches on its own).
- `defaults()` holds the attributes `build()` consumes to construct the Aggregate, plus a fallback generator for every key a modifier's own optional parameter falls back to when that modifier is called without overriding it. Every key `build()` actually consumes, with no exception (an `id`, a construction timestamp, anything), gets a matching `with<Key>()`, declared in the same order as `defaults()`'s own keys — whether or not a test currently needs to override it. A required attribute with no `defaults()` entry (e.g. `hasher`, declared as an optional key on the class's own `Attributes` shape, asserted via its private accessor) still gets its `with*()`, placed after the `defaults()`-backed ones. A key that exists solely as a modifier's own fallback (never read by `build()`) never gets a `with<Key>()` of its own — overriding it only ever makes sense together with calling that modifier, which is exactly what the modifier's own optional parameter already is for.
- Every state-transition method the aggregate exposes gets a matching modifier, declared in the same order as the aggregate's own methods — a transition with no modifier is a gap, not an intentional omission.
- A modifier's own optional override parameter (a timestamp, an amount, a reference, a label/reason) is never hardcoded inline — always an overridable parameter backed by a matching `defaults()` entry. Two or more optional parameters on the same modifier combine into one `withAttributes(...)` call before registering the modifier, via `array_filter([...])` dropping the `null` ones and spreading the rest as named arguments; a single optional parameter uses a ternary instead (`null !== $x ? $this->withAttributes(x: $x) : $this`). The modifier's closure takes the built Aggregate and the Builder itself (`static fn ($aggregate, self $builder) => ...`), reading every value back through array access (`$builder['key']`) — never a captured local variable, never a raw merged array. A required key with no `defaults()` entry is read via a private typed accessor (`Assert::isInstanceOf()`), called from both `build()` and every modifier that needs it — never a repeated inline check.
- A modifier that generates its own arbitrary value with no natural default (a tracking reference, a rejection reason via Faker) computes it unconditionally and stores it via `withAttributes()` before registering itself, declaring that key `?` (optional) on the `Attributes` shape — never in `defaults()`.
- A key is read off an already-built Builder instance through array access (`$builder['id']`), generically typed (`@template TName of key-of<TAttributes>` / `@return TAttributes[TName]`) so the call site gets the exact per-key type back with no `@var`/cast — used both inside a modifier's own closure and at a test's own call site, and may be written inline at each call site with no intermediate variable. The underlying per-key accessor stays `private`, reachable only through array access or the static `sample()` — never called directly, which would bypass the one contract those two entry points enforce. What stays forbidden inline is the Builder's own construction (`X::new()...`): that happens once in `// Given`, assigned to a named variable, never passed as a call argument.
- The static `sample(string $name)` is the only accessor for a test where `create()`/`store()` are never called on that Builder at all — no Builder instance is ever constructed, no matter how many distinct keys are needed (an id, a label, a keyId, a secret all belonging to one dispatched Command each get their own `sample()` call). A value needed only once always stays inline at its call site — a `// Given`-declared variable for a value read exactly once adds a name with nothing left to reuse it for; a value needed again later (a Command argument also checked back in `// Then` against a Finder read, a uniqueness registry seeded with a value dispatched later) is captured in a plain local variable on its one `sample()` call and that variable is reused — never a second `sample()` call expecting the same value back, since each call draws an independent fresh one. Array access on a Builder instance is reserved for the opposite shape entirely: the test itself calls `create()` and `store()` on that instance, and later reads one of its keys back to verify a Finder/projection reflects what was actually persisted — a real built-and-stored aggregate to tie the read to, never merely "more than one key is needed."
- A value read back for a later assertion always goes through the Builder instance (`$builder['key']`) — the test keeps the Builder itself in a local variable so that read stays reachable after `create()`/`store()` — never through the built Aggregate's own accessor as a substitute, even where one exists: uniform sourcing beats a per-case choice between the two. A `with*()` override on the Aggregate's own identity exists for the opposite case: forcing/sharing a specific, predetermined value — not for reading a value back afterward. The one exception is a Value Object/validation-compound test, where the literal itself is the scenario under test and no Builder is involved at all.
- `// Given` (state setup) is a Builder method call; `// When` (behavior under test) is a direct call on the Aggregate returned by `create()`.
- `create()` returns one Aggregate; `new()->many(n)->create()` returns `list<Aggregate>` through `Support\Builder\AggregateListBuilder` — `many(n)` broadcasts one shared attribute override to every item, so it can't vary a per-item field genuinely tied to a `with*()` call (e.g. a sort-key label) — the creation-timestamp attribute is exempt from this limitation, since it's computed fresh per item through `defaults()` rather than broadcast.
- A Builder never persists — `create()`/array access/`sample()` only ever build or read back in-memory state. Persisting is always `$this->store(...)` (`Support\TestCase\EventSourcingTrait`, see CQRS/container below), called on the built Aggregate(s) after `create()`.
- Two branches in the same test that would otherwise repeat an identical modifier prefix of 3 or more calls before diverging on one trailing call (or one call's argument) share that prefix as a single instance instead, reassigned under the subject's own variable name as it advances — a Builder's immutability guarantees the earlier reference stays untouched once a later call branches off it. Never collapse the prefix when either branch's own modifier argument differs at the shared depth (that difference is real signal, not duplication), nor when the second branch is a decoy deliberately left at its own baseline (no modifiers at all) rather than mirroring the subject's progression — merging that case would make the decoy start resembling the subject instead of staying an untouched control.

### Test doubles
- An integration test's double strategy follows its own subject, never a collaborator's cost or determinism. A storage-boundary test (Repository/Finder/Projector) has its own round-trip to storage as sole subject: a service collaborator needed merely to build a valid Aggregate through its Builder is doubled, deterministically — its own correctness belongs to that service's own dedicated test. A Value Object carried across that same boundary is never doubled this way, it's the data under test, not a service. A use-case test (a Command/Query Handler, or an Application port exercised directly by a Delivery Mechanism) has the whole orchestration as its subject instead: every in-process collaborator is wired for real; only a boundary actually leaving the process (a vendor call, a transport) gets doubled there.

### Event Sourcing (`Patchlevel\EventSourcing\PhpUnit\Test\AggregateRootTestCase`)
- `given(...events)->when(fn (Aggregate $a) => ...)->then(...expectedEvents)` — the standard shape for an aggregate unit test.
- `expectsException(...)` replaces `then(...)` for a failure case.
- Every timestamp in the test is expressed as `$now->modify('+1 day')`/`modify('-2 hours')` off one local anchor, never a separate hand-typed `\DateTimeImmutable` literal per fixture — this test never touches a Builder or the container, so the anchor stays a fixed local literal, never `Clock::get()->now()` itself. Its value matches the suite-wide frozen instant (`$now = new \DateTimeImmutable('2026-01-01T00:00:00+00:00')`, the same instant `ClockExtension` freezes `Clock::get()->now()` to) — a different, arbitrary "today" per test file reads as two disconnected eras across the same suite for no reason, even though nothing here actually calls the frozen clock. Each `modify()` delta itself must read as a plausible real-world gap for what it represents (a shipment manifested hours after preparation, never open-endedly far apart) — a boundary case straddles its threshold by a small, deliberate margin on each side, not an arbitrary offset picked for arithmetic convenience.

### CQRS / container (`Support\AbstractIntegrationTestCase`)
- `dispatch()` sends a Command to the Command bus; `ask()` runs a Query and returns its result.
- `service()` resolves a service from the container with a type assertion on the given class/interface. `serviceAs()` resolves a service whose container ID differs from the PHP type it's expected to be (e.g. a Doctrine alias).
- A Policy or Processor is exercised directly — construct/fetch it and invoke it with the event it subscribes to — rather than relying on a running subscription worker in the test suite.
- `store()` persists and triggers the `publisher` then `projector` groups (never the `#[Policy]`/`#[Processor]` side effects).
- `publishedEventOf(string $eventClass)` returns the persisted event of that type, scanning the whole store.
- A check against "now" that's a passive, non-reactive comparison (an `expiresAt`/TTL field read at query time, no `#[Policy]`/cron triggered by the passage of time) is tested with a deliberately far past/future static date on the Builder — real wall-clock time, no clock involved. A check whose SUT holds an injected `Psr\Clock\ClockInterface` for behavior that genuinely reacts to time passing, or needs a precise boundary, reads `Clock::get()->now()` as its anchor, same as everywhere else — the suite-wide `ClockExtension` already freezes `Symfony\Component\Clock\Clock`'s global singleton to one fixed instant before any test runs, and the container's own `clock` service has no inner clock of its own, so it already proxies that same frozen singleton. A test never overrides the container's `clock` service with its own `MockClock` instance — that creates a second, independent clock diverging from `Clock::get()->now()`, which every Builder default already reads from.
- Every fixture timestamp in a test is expressed as `$now->modify('-2 hours')`/`modify('-3 days')` off that one frozen `Clock::get()->now()` anchor — never a second, independently hand-typed `\DateTimeImmutable` literal per fixture. The delta itself must read as a plausible real-world gap for what it represents (an order refunded hours or days after capture, never open-endedly far apart) — a `stuck`/`fresh` pair straddles the threshold by a small, deliberate margin on each side, not an arbitrary date picked for arithmetic convenience.
